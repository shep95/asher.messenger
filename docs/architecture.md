# Architecture

## Components and how they talk

```
                 ┌────────────────────────── clients ──────────────────────────┐
                 │  Android (Kotlin)      iOS (Swift)        Desktop (Electron) │
                 │       │                    │                    │            │
                 │       └──────── libsignal (Rust core + bindings) ┘           │
                 └───────┬──────────────┬───────────────┬────────────┬──────────┘
        REST + websocket │      HTTPS   │      HTTPS    │   Noise/WS │  Noise/WS
                         ▼              ▼               ▼            ▼
                 services/server   services/storage   CDN (S3)   services/cdsi
                 (Signal-Server)   (storage-service)             services/svr2
                    │      │                                         (enclaves)
        gRPC        │      │ shared-secret tokens
                    ▼      ▼
      services/registration  ──► SMS / voice providers
                                                          services/calling (SFU) ◄── ringrtc in clients
```

* **libsignal** is the one dependency every client shares. Besides the Signal
  Protocol and zkgroup it contains `libsignal-net`, which owns the chat
  websocket, contact discovery, SVR and key-transparency connections. Its
  environments are compiled in; see `rust/net/src/env/brand.rs` for the brand
  override.
* **Signal-Server** is the account/message hub. It never talks to CDSI or SVR
  on the clients' behalf; it only mints the shared-secret auth tokens clients
  present to those services. Registration is delegated to
  `registration-service` over gRPC. Groups and encrypted settings live in
  `storage-service`, which needs the same zkgroup server params.
* **Calling**: 1:1 calls are peer-to-peer WebRTC via ringrtc with TURN from
  the server config; group calls go through the SFU in `services/calling`.
* **Data stores** (server): DynamoDB (33 tables), Redis Cluster ×4 + Redis ×1,
  FoundationDB for the message queue, S3/GCS for attachments, prekeys and
  dynamic config. See `docs/self-hosting.md`.

## What a brand changes, per layer

| Layer | Mechanism | Committed state |
|---|---|---|
| libsignal | `LIBSIGNAL_BRAND_*` env at build time (`libs/libsignal/brand.env`, generated) | Upstream + override module; inert without the env |
| Android | `clients/android/brand.properties` (generated) read by `app/build.gradle.kts`; `strings.xml` rewritten | Upstream values |
| iOS | `project.pbxproj`, `TSConstants.swift`, `Info.plist`, entitlements, `.cer` rewritten | Upstream values |
| Desktop | `package.json`, `config/production.json`, `_locales/en/messages.json` rewritten | Upstream values |
| Server | `deploy/server/<brand>/config.yml` generated; `GrpcExceptions.DOMAIN` rewritten | Upstream values |

`tools/brand/apply.py` is the only writer for all of these, and
`brands/signal-upstream` is the profile that produces the committed state.

## Trust and keys

A brand deployment owns five kinds of key material, all generated by
`tools/server/gen-keys.sh`:

1. **zkgroup ServerSecretParams** (server, storage-service) ↔ `ServerPublicParams` (clients: `zkgroup_server_public_params`).
2. **GenericServerSecretParams** for calling and for chat/backups ↔ public halves (`generic_server_public_params`, `backup_server_public_params`).
3. **Unidentified-delivery CA** ↔ CA public key (clients: `ud_trust_roots`); the server holds a certificate signed by it.
4. **TLS root CA** for all service hosts ↔ pinned in every client (`crypto.root_ca`).
5. **Enclave measurements** (MRENCLAVE) of your CDSI/SVR builds, plus shared secrets between server and each enclave service.

Signal's own values for 1–5 are what the upstream apps carry; none of them
will accept a third-party server, which is why every one of them is a field in
`brand.json`.
